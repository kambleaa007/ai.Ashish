## 2. Agent Loop Engineering Fundamentals

### 2.1 What is Agent Loop Engineering?

Agent Loop Engineering is the practice of designing, building, and optimising autonomous AI agents that work through a repeating execution cycle. Instead of answering a question once and stopping, the agent repeatedly observes the current situation, reasons about the next step, performs an action, evaluates the result, and continues until the task is complete.

### 2.2 Core Loop Architecture

Nishi described the agent loop as consisting of four recurring phases:

1. **Perception** â€“ The agent reads input, gathers context, extracts useful information, and understands the current state.
2. **Planning / Reasoning** â€“ The agent decides what should be done next based on the goal and available context.
3. **Action** â€“ The agent executes a tool, API call, workflow, or backend operation.
4. **Evaluation / Reflection** â€“ The agent checks whether the action result is valid, whether the task is complete, and whether another loop iteration is needed.

This approach enables agents to handle complex, multi-step tasks autonomously and shifts some responsibility for handling edge cases from human programmers to engineered AI-agent loops.

## 4. Perception and Context Window Engineering

Nishi used the example of an AI legal assistant analysing a large corporate contract to explain the perception phase.

### 4.1 Large Document Processing

The agent may need to analyse a 500-page corporate contract and extract only liability-related risks. Since an LLM cannot practically process all pages at once without performance or memory issues, the system needs structured input-handling strategies.

### 4.2 Context Window Engineering

Key techniques discussed included:

- **Sliding Window** â€“ Feeding the LLM small chunks of the document, such as 10 pages at a time.
- **Summarisation Chains** â€“ Creating summaries section-by-section and combining them.
- **Retrieval-Augmented Generation (RAG)** â€“ Fetching only the specific clauses relevant to the userâ€™s question, such as liability clauses.

### 4.3 Async Local Storage

Nishi explained that when multiple users interact with the same AI assistant, such as multiple lawyers analysing different contracts, the backend must isolate their sessions. Async local storage can act like a secure tracking thread for each user request, ensuring that one userâ€™s contract data does not leak into another userâ€™s prompt or response.

### 4.4 Stream Processing

Instead of downloading and loading the full document into server memory, readable streams can process the document line by line or chunk by chunk. This reduces the risk of server crashes and enables large files to be processed more efficiently.

### 4.5 State Serialisation

If a server crashes or restarts midway through processing, such as on page 250 of a 500-page document, the agent should not lose progress. Intermediate state and extracted findings can be continuously serialised into stores such as Redis or PostgreSQL, allowing the system to resume from the last processed point.

### 4.6 Signal Filtering and Preprocessing

Before sending text to an external LLM, a preprocessing pipeline should scan and clean the input. This includes:

- Removing personally identifiable information (PII).
- Removing corporate bank account numbers or other sensitive information.
- Removing irrelevant headers, footers, margins, and formatting noise.
- Sending only clean, safe, and relevant legal language to the model.

## 5. Orchestration, Reasoning, and Structured Engineering

Nishi explained orchestration and structured engineering using an AI customer-support agent managing e-commerce refunds.

### 5.1 Prompt Engineering as Code

Instead of storing prompts casually in text files, prompts should be treated like software code. This means prompts can be:

- Version-controlled in Git.
- Dynamically injected with parameters.
- Tested and maintained like application logic.

For example, a refund prompt may receive customer tier, item price, item code, and return policy inputs so that the model can determine whether VIP or standard return rules apply.

### 5.2 Structured Output and Validation

Nishi discussed the importance of forcing LLMs to produce predictable structured outputs rather than conversational responses.

For refund processing, the backend may require JSON fields such as:

```json
{
  "refundApproved": true,
  "amount": 500,
  "reason": "Eligible return within policy window"
}
```

Validation libraries such as **Zod** can ensure the output contains the exact required fields and follows the expected schema.

### 5.3 Streaming JSON Parsing

Waiting for a full JSON object to be generated can make an application feel slow. A streaming JSON parser can read and parse the output as it is generated character by character, updating the UI in real time without blocking the application loop.

### 5.4 Tool Selection Logic

Nishi explained that the LLM may decide whether a refund is valid, but it should not directly process money. Instead, the backend translates the LLMâ€™s intent into API calls and routes the operation to internal microservices such as payment processing, inventory updates, and database queries.

## 6. Action Phase: Reliability and Security Mechanisms

Nishi discussed the action phase using a financial data-analysis agent that writes code to process financial transactions and update a company ledger.

### 6.1 Sandboxing for Code Execution

LLM-generated code can contain errors or unsafe behaviour. Therefore, generated code should run inside an isolated environment or sandbox.

Benefits of sandboxing:

- Prevents access to host server files.
- Blocks unauthorised network access.
- Protects against malicious scripts.
- Allows code execution in a controlled quarantine environment.

### 6.2 Idempotency in Transactions

Nishi used the example of transferring â‚¹5,00,000 and encountering a network disconnection halfway through the process.

To prevent duplicate transactions during retries, systems attach a unique idempotency key to each request. The receiving system recognises repeated requests with the same key and processes the transaction exactly once.

### 6.3 Concurrency Control with Queues

If an agent needs to fetch stock data for many companies at the same time, sending all requests simultaneously may trigger API rate limits. A queue system can control traffic by allowing only a fixed number of concurrent requests, such as five requests at a time.

### 6.4 Saga Pattern for Multi-Step Workflows

Nishi explained the saga pattern using order processing:

1. Reserve inventory.
2. Charge the card.
3. Generate the shipping label.

If the shipping service fails after the card has been charged, the saga pattern triggers compensating actions, such as refunding the card and returning inventory to stock. Nishi compared this to rollback behaviour with save points.

## 7. Reflection and Governance in Agent Loops

The reflection phase was explained using a healthcare AI assistant managing patient intake, insurance verification, and long-term care planning.

### 7.1 Critic Models for Validation

A primary AI agent may draft a prescription or recommendation based on symptoms. Before the recommendation reaches a doctor or end user, a secondary critic model or validation script reviews it to catch harmful interactions, unsafe suggestions, or errors.

### 7.2 Event Sourcing and Temporal Debugging

Instead of simply overwriting system state, every small action should be logged as an immutable event. This allows developers to:

- Rewind to earlier states.
- Inspect what happened at each step.
- Debug errors more effectively.
- Support undo and correction workflows.

### 7.3 Graceful Degradation and Human-in-the-Loop

If automation fails, such as when an insurance website changes its layout and the agent can no longer verify policy information, the system should not crash or hallucinate. Instead, it should fall back to a human-in-the-loop process, such as creating a support ticket for manual review.

### 7.4 Memory Consolidation for Long-Term Context

Short-term memory helps the agent track a live conversation, while important long-term information can be saved into a vector database. For example, a healthcare assistant may clear temporary chat history after a session but retain key patient history for future continuity.

## 8. Safety, Resilience, and Cost Control in AI Agents

Nishi covered safety, resilience, and cost control using the example of an autonomous cloud infrastructure agent helping engineering teams manage, monitor, and clean up resources.

### 8.1 Input-Output Filtering and Prompt Injection Defence

When developers ask an agent to analyse server logs, preprocessing middleware should scan the logs before sending them to the LLM. It should remove:

- Database passwords.
- Credentials.
- Sensitive internal values.
- Hidden malicious commands.
- Prompt-injection attempts.

### 8.2 Circuit Breakers for Service Outages

If the underlying LLM provider experiences an outage or severe slowdown, a circuit breaker library such as Opossum can detect the failure, stop additional requests, and display a temporary service-degradation message rather than freezing the full dashboard.

### 8.3 Token and Cost Rate Limiting

The session covered the risk of runaway loops where an agent keeps retrying and consuming tokens. A token bucket algorithm can monitor usage per team or user and stop execution once hourly token or cost limits are exceeded.

### 8.4 Human-in-the-Loop for High-Impact Actions

For destructive or high-impact actions, such as deleting an inactive database, the system should pause and request explicit human approval. The agent should not execute such actions independently.

## 9. Agent Engineering Patterns

Nishi introduced several engineering patterns useful for production-grade AI agents.

### 9.1 State Machines / XState

State machines define strict states and valid transitions. For example, in a banking onboarding workflow, an agent should not move directly to account approval unless identity verification has completed successfully.

### 9.2 Worker Threads

Heavy tasks such as comparing thousands of transactions against a fraud blacklist should not block the main Node.js event loop. Worker threads allow CPU-intensive work to run separately while the main server continues handling incoming requests.

### 9.3 Dependency Injection

Dependency injection helps decouple core business logic from external LLM providers. During local testing, developers can inject a mock LLM service. In production, the system can swap in a real LLM provider without changing the core application logic.

### 9.4 Type-Safe Tool Definitions

Nishi explained that tool definitions can be written using TypeScript and automatically converted into JSON schemas understood by LLMs. This prevents mismatches between backend function signatures and the schema exposed to the model.

## 11. Resilience Patterns for AI Systems

Nishi explained resilience using a medical billing and health-insurance claim processing example.

### 11.1 Grounding Constraints

If an LLM invents a non-existent insurance code, a backend script should cross-check the proposed code against an official verified database or vector store. If the code does not exist, the system rejects the answer and forces the model to choose only from verified results.

### 11.2 Timeouts and Retry Strategies

For slow or unreliable APIs, systems should apply strict timeouts and retries with exponential backoff and jitter. Example strategy:

- Timeout after a fixed duration.
- Retry after 2 seconds.
- Retry again after 4 seconds.
- Retry again after 8 seconds.
- Add random jitter to avoid overwhelming the service.

### 11.3 Fallback Models

If the primary LLM provider fails or returns errors, the backend can route the active state and prompt context to a secondary fallback model or provider.

### 11.4 Dead Letter Queues

If a task repeatedly fails after the maximum retry count, the system should stop the loop, serialise the full state, and push the task to a dead letter queue. This prevents one broken task from blocking the rest of the pipeline and allows a human specialist to review it later.
