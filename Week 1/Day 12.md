## 2. Main Discussion Points

## 2.1 Why GitHub Actions Is Important

The meeting began with a real-world style explanation of the risks involved in manual deployments.

Nishi described scenarios where an engineer manually connects to production, makes a small change, and accidentally causes a production outage. Examples included:

- Accidentally deploying broken code.
- Making a typo in a database migration script.
- Exposing database credentials or passwords.
- Wiping out an important database table.
- Taking several hours to recover from backup.
- Losing customer trust due to downtime and security incidents.

The key point was that manual deployment creates risk because humans can make mistakes, especially during urgent production fixes.

GitHub Actions was presented as an automated safety layer that helps teams avoid these issues by enforcing checks before code reaches production.

---

## 2.2 GitHub Actions as an Automated Gatekeeper

GitHub Actions was described as a form of automated gatekeeper for software delivery.

Instead of allowing developers to directly touch production servers, GitHub Actions encourages teams to use pull requests, automated tests, linting, integration checks, and security scans before merging or deploying code.

Important benefits discussed:

- Broken code can be blocked before merging.
- Tests can detect failures early.
- Secret scanning can detect leaked passwords or API keys.
- Standardised runners remove environment differences between developer machines.
- CI/CD provides a controlled and repeatable deployment process.

---

## 2.3 GitHub Actions Core Concepts

The trainer explained the key building blocks of GitHub Actions.

### Workflow

A workflow is an automated process defined in a YAML file inside the `.github/workflows` directory of a repository.

### Event

An event is a trigger that starts a workflow. Examples include:

- Code push.
- Pull request creation.
- Scheduled workflow execution.

### Job

A job is a set of steps that run on the same runner. Jobs can run independently or in sequence depending on the workflow configuration.

### Step

A step is an individual task inside a job. Steps run sequentially and can execute shell commands or use reusable actions.

### Action

An action is a reusable plugin or command that performs a specific task in a workflow.

### Runner

A runner is the machine that executes the workflow. It can be GitHub-hosted or self-hosted.

- **Runner**: The environment where the recipe is executed.

## 3.4 Important AI Governance Rule

A key point repeatedly emphasised was:

> AI is an assistant, not the boss.

The trainer explained that AI-generated workflows must not be pushed blindly to production.

Human review is mandatory because AI may:

- Use outdated actions.
- Misconfigure secrets.
- Generate incorrect YAML.
- Produce workflows that look correct but are not secure or production-ready.

Recommended review checks:

- Verify whether the action name and version actually exist.
- Check whether the workflow follows least privilege.
- Confirm that no secrets are leaked in logs.
- Test the pipeline in a safe environment first.

## 4. Secrets Management and Security

## 4.1 What Counts as a Secret

The session covered examples of secrets that must not be committed to source code:

- API keys.
- Database connection strings.
- Personal access tokens.
- Passwords.
- Cloud credentials.
- Private keys.
- Webhook URLs or other sensitive endpoints.

---

## 4.2 Types of GitHub Secrets

### Repository Secrets

Repository secrets are available to workflows inside a specific repository. They are encrypted when stored.

### Environment Secrets

Environment secrets are scoped to a specific environment such as production. They can be protected by approval rules before being used.

### Organisation Secrets

Organisation secrets are centrally managed and can be shared with selected repositories. This avoids copying the same secret into many repositories.

---

## 4.3 Security Best Practices

The following best practices were discussed:

1. Use least-privilege permissions.
2. Configure the `permissions:` block in workflow YAML.
3. Do not give workflows unnecessary write or delete permissions.
4. Never print secrets using `echo`.
5. Use masking such as `add-mask` for dynamically generated sensitive values.
6. Use OpenID Connect (OIDC) instead of long-lived hard-coded cloud credentials.
7. Enable secret scanning.
8. Use static application security testing where appropriate.
9. Treat AI-generated YAML with the same review process as human-written code.

## 5. Rollback Strategies

## 5.1 Golden Rule of Rollback

The trainer explained that reliability is not only about never making mistakes. It is also about how quickly the team can recover when something goes wrong.

The key recovery metric discussed was speed of recovery, also described as MTTM â€” mean time to mitigate.

Every deployment should have an emergency rollback plan.

---

## 5.2 Rollback Strategies Discussed

### Blue-Green Deployment

Two identical environments are maintained:

- Blue: current stable version.
- Green: new version.

Traffic can be switched instantly between them. If the new version fails, traffic can be switched back quickly.

### Canary Deployment / Rollout

A new version is released to a small percentage of users or servers first. Monitoring checks for errors. If errors increase, deployment can stop and roll back automatically.

### Rolling Update

Servers or instances are updated in batches. For example, only a small portion of the system is updated at a time while the rest continues serving traffic.

### Redeploy Artefact

The previous successful build or artefact is redeployed when the new version fails.

### Feature Flags

A feature is deployed but controlled by a remote toggle. If the feature causes issues, it can be turned off without changing infrastructure.

---

## 5.3 Rollback Implementation Methods

The trainer also discussed ways to implement rollback in GitHub Actions:

### Manual Trigger

A human engineer manually triggers a rollback workflow, often using `workflow_dispatch` with a specific version input.

### Automated Rollback

Monitoring detects failures and automatically rolls back to a previous stable version.

### Tag-Based Rollback

A stable Git tag is moved or reassigned to a previous working commit or release.

---

## 5.4 Post-Rollback Protocol

After rollback, the team should not stop immediately. The following post-rollback activities were discussed:

1. Run smoke tests automatically.
2. Notify the team or incident channel.
3. Open an incident review.
4. Investigate why the issue happened.
5. Identify how the issue passed testing.
6. Define prevention steps for future releases.
